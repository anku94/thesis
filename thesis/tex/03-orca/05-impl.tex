The core ORCA framework consists of 40K lines of code (80\% C++, 20\% Rust).
ORCA uses the Mercury~\cite{Souma2013:MercuryRPC} RPC library for on-fabric communication via
libfabric~\cite{Grun2015:libfabrica} and UCX~\cite{Shami2015:UCX} providers.
The Rust portion consists of OrcaFlow's DataFusion-based query planning and execution on each node,
while the bulk of the functionality --- bootstrap, transport, and control --- lies on the C++ side.

\subsection{Implementation Overview}

\pplushead{Integration}
Two integration surfaces exist: the \orcaclient{} shim for applications, and collectors for
profiling interfaces.

\begin{itemize}[leftmargin=*]
  \item \emph{OrcaClient:}
        The \orcaclient{} shim links with the application and exposes a \ocpta{} hook, called after every
        timestep.
        ORCA can be activated at runtime by preloading the full library, otherwise these hooks become
        noops.
        \ocpta{}  captures all data path work, including draining collectors, executing
        tier plans, dispatching data, and handling control messages.

  \item \emph{Collectors:}
        Streams are defined by collectors --- they accumulate events locally and emit Arrow dataframes when
        drained.
        At the end of each timestep, ORCA drains all collectors and enqueues the output for analysis.
        Our implementation currently packages basic collectors for MPI~\cite{:MPI} and
        Kokkos~\cite{Trott2022:Kokkos3}.
        Additional collectors may be defined by clients.
        Collectors can also implement dynamic instrumentation via interfaces like eBPF~\cite{:eBPF} and
        DynInst~\cite{Berna2011:DynInst}.

\end{itemize}

\pplushead{Overlay}
The ORCA overlay bootstraps via a TCP-based protocol and swiches to on-fabric RPCs after the
initial handshake.
% While the overlay supports additional topologies, only one is discussed in this paper for
% simplicity.
% The ORCA overlay bootstraps via a TCP-based discovery protocol for the initial handshake with the
% controller, and then switches to on-fabric RPCs once Mercury addresses are exchanged.
Routes are then constructed as per the selected TBON topology, and available aggregators are
automatically assigned to ranks.
Each overlay entity is assigned a 32-bit ID called \texttt{ovid} to enable uniform addressing
across all tiers.
Multiple topologies are supported, including \topodir{}, where all MPI ranks directly connect to
the overlay, and \toporep{}, where ranks choose node-local representatives to reduce aggregator
incast.
Additional topologies can be plugged into the framework.
For simplicity, we only discuss the \topodir{} topology in this paper.

\pplushead{Data Path}
The data path is completely asynchronous but timestep-ordered --- each node at every tier executes its tier plans
on dataframes in timestep order independently, executes local sinks, and forwards 
relevant data to the next tier.
Despite its asynchronous nature, flow updates across tiers also guarantee timestep-consistency.
We now describe two examples of properties conferred by the TBON that the planner understands:

\begin{itemize}[leftmargin=*]
  \item \emph{Partitioning:}
        The default reduction behavior is a partition-preserving merge. Each node's subtrees
        emit rank-partitioned data --- merge preserves
        this partitioning.
  \item \emph{Sortedness:}
   Merging does not preserve sortedness by default, even if the inputs are sorted. As a result,
   plan operators that require sorted inputs must not be pushed down to lower tiers.
\end{itemize}

\subsection{TS2PC: Implementation Details}
\label{sec:orca:impl-ctl}

TS2PC is implemented as separate \emph{inner} and \emph{outer} layers.
The inner layer enables a single transaction with a unique monotonic ID called \texttt{txnseq},
targeting a particular $T_{cmd}$.
The outer layer adds features like $\Delta$-learning, automatic retries, and cross-tier
consistency.

\parahead{Handling Pauses}
The control plane supports pausing and resuming the application between timesteps as primitives for
more complex workflows.
An interesting case emerges from the interaction of the paused state with TS2PC --- when a resume
is committed, it will be enqueued to be applied at a future timestep never reached by a paused
application, creating a deadlock.
Our solution recognizes that the paused state makes the application synchronous with the user and
renders TS2PC unnecessary for consistency --- commands in this state circumvent the protocol and
are executed directly.

\parahead{Cross-tier Consistency}
Commands such as flow updates trigger tier plan updates at all tiers, and must be applied at a
consistent timestep across the entire TBON.
This is challenging as the higher tiers are asynchronous and observe timesteps at different times
--- tiers are defined to observe a timestep when they process its dataframes.

Cross-tier consistency is supported via control \emph{domains} in the outer layer.
% allowing the entire overlay to be addressable via timestep-consistent control.
Each tier corresponds to a domain, and each transaction contains a bitmask for its executing
domains --- flow updates, for example, apply to all domains.
Regardless of the domain, all TS2PC commit decisions are made by \tiermpi{}, treating it as the
single source of truth on the application timestep.
Higher tiers snoop on protocol traffic and apply commands only if their domain bit is set.
