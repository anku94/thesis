Beyond observability, ORCA's design reflects a broader convergence between OLAP and HPC:
columnar formats~\cite{:ApacheArrow, :ApacheParquet}, SQL planning, and embeddable query
engines~\cite{Lamb2024:DataFusion} applied to in-situ HPC analytics.
Compared with prior in-situ systems, ORCA differs in two ways.
First, instead of placing analytics entirely on application
ranks~\cite{Zheng2018:DeltaFS,Jain2024:CARP} or entirely on a dedicated
tier~\cite{Eisen2024:ADIOS}, ORCA's planner decomposes them into operators that can be placed on
either tier at runtime.
Second, unlike ADIOS-style offload as a peer MPI job~\cite{Eisen2024:ADIOS}, ORCA's analytics tier
is fully asynchronous while still preserving timestep-consistent semantics.

\section{Steerable Observability: Retrospective and Synthesis}\label{sec:concl:retrospective}


Steerable observability is the ability to request runtime views of application state, reconstructed
in real time, and to change those views on demand as diagnosis progresses.
% We define steerable observability as the ability to request runtime views of application state,
% reconstructed in real time, with the ability to change requested views on demand. This makes
% always-on collection viable for production BSP systems: high-level signals flag anomalies in real
% time, and narrower views can then surface their root causes. The same paradigm enables online
% intervention, as views are both necessary to guide interventions and assess their effectiveness.
Its core contribution is economic.
Conventional tracing is locked to a preselected fidelity that both overcollects and undercollects:
despite paying for comprehensive collection at one layer, it can still lack the
visibility into lower layers necessary
for root-cause identification.
Steerable observability shifts the cost model by evaluating predicates and reductions before
export, so only matches and summaries pay serialization, transport, and storage.
This makes needle-in-haystack questions viable as continuous queries, and supports drill-down
across arbitrary fidelities as needed, insofar as instrumentation permits.



\paragraph{BSP Is Different}
BSP workloads run as a single coordinated job, not a web of loosely coupled microservices.
Global synchronization defines both the unit of work and the axes of causality and consistency.
Attribution of pathologies is first to a straggler rank, then to the sequence of events behind its
slowdown.
Root causes lie within a deeper layer of the same runtime stack, not across microservices.
Analyses need to preserve these causal dependencies.
Event-based streaming systems treat
events as separate in transit, requiring these dependency edges to be reconstructed after
collection.

ORCA is co-designed for this paradigm, translating queries into an execution strategy
that approaches the minimum necessary work --- data movement is minimized via pushdowns that
leverage the application's scale, and RDMA minimizes
the overhead of residual data movement.
All processing happens in-memory over a highly efficient columnar representation.
The closest analogs are \emph{Data Acquisition} (DAQ) pipelines in particle
accelerators~\cite{Aboli2016:DAQ-ATLAS,Bauer2012:DAQ-CMS}, where
FPGAs discard the bulk of sensor data at source, retaining only high-signal telemetry.
Fay~~\cite{Erlin2011:Fay} and Snicket~\cite{Berg2021:Snicket} implement query-driven tracing for
microservices.
ORCA extends this to BSP workloads, adding a
control plane for steerability.

\paragraph{Steerability Limits}
Feedback-driven mechanisms have an inherent latency floor: collection, reduction, and transport
take physical time.
ORCA eliminates the artificial costs that dominate today---ETL and unnecessary data
movement---but cannot circumvent this floor.
Some regimes demand action faster than any global view can be assembled.
Network congestion control algorithms, for instance, are designed explicitly around partial
observability~\cite{Jacob1988:CCAPartial}.
When conditions are too transient for online intervention, ORCA's in-situ reductions still capture
their structure more efficiently than any post-hoc approach, providing the empirical basis for
developing predictive strategies that anticipate rather than react~\cite{Smith1957:Predict}.


\section{Immediate Extensions}\label{sec:concl:extensions}

\paragraph{Instrumentation Sources}
Tools like Kineto~\cite{2025:PytorchKineto} aggregate telemetry from multiple sources into a
unified trace.
ORCA supports the same but as real-time aggregations over any interface that emits structured
events---NVTX/CUPTI GPU hooks, MPI runtime probes, hardware counters.
eBPF~\cite{:eBPF} and DynInst~\cite{Berna2011:DynInst} are especially appealing as they enable dynamic instrumentation without
recompilation, extending visibility into arbitrary functions at runtime.

\paragraph{Approximate Summaries}
Mergeable sketches can summarize streams in-flight at far lower cost and fit naturally into ORCA’s
reduction topology.
For example, KLL~\cite{Karni2016:KLLSketch} can estimate latency percentiles, and
Count-Min~\cite{Cormo2005:CountMin} can
identify heavy hitters such as straggler ranks or hottest callsites, all with bounded error and
without retaining raw events.

\paragraph{Shuffling-Based Streaming Analytics}
Shuffling-based in-situ indexing systems like DeltaFS~\cite{Zheng2018:DeltaFS} and
CARP~\cite{Jain2024:CARP} show that hash and range
partitioning can reorganize scientific data effectively at scale.
ORCA can treat these shuffles as intra-tier operators within its topology, so they compose cleanly
with inter-tier reductions in a single plan.
Because the MPI tier has substantial egress bandwidth, the planner can be
phase-aware, scheduling sinks at the MPI tier in checkpoint phases while avoiding that
interference during compute phases.

\paragraph{Open Table Formats for HPC}
While ORCA writes telemetry as partitioned Parquet, it does not currently emit a metadata catalog.
Open table formats such as Iceberg~\cite{:Iceberg} maintain a lightweight index over partitioned
Parquet
files---partition boundaries, column statistics, file locations---enabling engines to prune
irrelevant data without scanning.
Any HPC pipeline that already writes Parquet would benefit from the same treatment, replacing ad
hoc file-management conventions with self-describing, immediately queryable datasets.

\paragraph{Control Interface Regularization}
The set of controllable actions is currently defined ad hoc per integration.
Regularizing this into typed providers that advertise capabilities, accept structured commands, and
return typed acknowledgments makes control capabilities discoverable and composable, analogous to a
southbound API in SDN.

\section{Future Directions}\label{sec:concl:future}

ORCA's current query model is relational: SQL over event streams, planned and placed across the
overlay.
The power of an algebraic approach is that complex pipelines reduce to compositions of well-defined
operators, each independently placeable and optimizable.
The directions below extend this principle to richer data types, deeper execution tiers, and
adaptive placement.

\paragraph{Beyond Relational Algebra}
Scientific computing and ML operate primarily on arrays,
meshes, and tensors using domain-specific analytics that go beyond the relational model.
Prior work on SciQL~\cite{Kerst2011:SciQL} and MeshSQL~\cite{Lee2004:MeshSQL} has explored
declarative interfaces for these types, and practical
convergence is underway through bridges like arrow-zarr~\cite{2026:arrow-zarr} and
Arrow$\leftrightarrow$DLPack~\cite{:DLPackProtocolApache}.
DataFusion's extensibility makes it possible to host array and mesh operators
alongside relational ones in the same query plan.
This also opens a path to expressing HPC visualization
workflows~\cite{Ayach2015:Catalyst,Larse2022:Ascent} as dataflows rather than separate
pipelines.
A related direction is observability over GPU-resident state such as model weights, where
device-side reductions would
emit compact summaries without transferring full tensors to the host.

\paragraph{Multi-Tier Compilation}
ORCA's overlay currently executes all operators on host-side aggregators.
Additional execution tiers are becoming viable: SmartNICs can run Arrow-native reductions on the
fabric itself~\cite{Ulmer2023:ExtendingComposableDatab,Liu2022:ProcessingParticleData}, and eBPF
can push filter and sketch logic into kernel-space probes.
Each tier admits a restricted operator subset under different resource and state constraints.
The compilation problem is decomposing a high-level query across these tiers---deciding which
operators run where and how intermediate results flow between them.

\paragraph{Cost-Aware Reactive Placement}
ORCA’s placement today follows tree the topology: per-partition work is pushed down, while
cross-partition work remains at higher tiers.
While this works, it is not cost-aware because it does not react to observed placement conditions
such as backlogs and kernel costs.
A natural extension is to feed these cost signals back into the planner and let it move operators
and sinks across tiers online.
This effectively makes ORCA self-tuning using the same observability machinery it provides to
applications.
