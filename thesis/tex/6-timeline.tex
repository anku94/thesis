\chapter{Thesis Completion Roadmap}
\label{chap:timeline}

ORCA is under advanced stages of development.
We first briefly describe the current state of the system, and then outline the remaining work
required to complete the thesis.

\section{Current State}

\paragraph{Completed Developmental Work}
Most core components of ORCA have been implemented.
Completed components include overlay bootstrapping with multiple aggregators and topologies,
telemetry collection and forwarding mechanisms, with per-timestep analytics semantics.
Observability requirements are programmed using a domain-specific language (DSL) called OrcaFlow:
the DSL enables defining transformations as SQL, applied in-situ while data is routed to
configurable \emph{sinks}.
The TS2PC protocol for the control path has been implemented.
End-to-end telemetry visualization is available via a DuckDB~\cite{Raasv2019:DuckDB} and a
FlightSQL~\cite{:ArrowFlightSQL} server embedded into the controller, streamed to
Grafana~\cite{:GrafanaDashboard}.
ORCA reuses the same infrastructure to export internal metrics for realtime visualization and
performance analysis.
Observability requirements from recent machine learning
literature~\cite{Jiang2025:TrainCheck} have been reviewed and incorporated in system
semantics.

\paragraph{Validated Capabilities}
A single-aggregator deployment of ORCA has been validated to be stable in a stress test with 128
MPI ranks loading the aggregator with 2--3 GB/s of telemetry.
Analytics were performed locally on the aggregator, achieving near-line rate performance under
ideal conditions on 40 Gbps Infiniband NICs.
Stress testing surfaced stability issues, which were mitigated by tuning pipeline parameters and
implementing flow control mechanisms.
We found basic Arrow-based in-memory analytics to be much faster than our ingestion rate.
The RDMA-based transport layer has been tuned and shown to be stable.

\paragraph{Remaining Developmental Work}
The primary remaining component is distributed query planning to fragment the OrcaFlow pipeline
across the overlay at operator-level granularity.
Development of the query planner is completed and integration with the overlay is underway.
% An initial prototype of the query planner exists but requires further refinement and integration.
Python bindings for Pytorch~\cite{Paszk2019:PyTorch} integration are also under development for the
planned experiments.

\section{Evaluation Roadmap}

The evaluation will demonstrate the practical benefits of ORCA's relational approach in terms of
query performance, system scalability, and end-to-end impact.
The plan consists of the following experiments:

\begin{itemize}
  \item \textbf{Microbenchmarks:}
        Compare query efficiency and analytical flexibility using on-disk Parquet~\cite{:Parquet} telemetry
        versus traditional trace formats.
        AMR-inspired queries~\cite{Jain2025:AMR} will serve as the HPC baseline, and Pytorch
        HTA~\cite{:HolisticTraceAnalysis} will be used as the ML baseline.
  \item \textbf{Synthetic stress tests:}
        Measure ORCA throughput and scalability as a function of aggregator count, and quantify application
        jitter as a function of data load.
  \item \textbf{End-to-end workload studies:}
        Measure runtime overhead and impact on scientific progress for a 4,096-rank AMR
        simulation~\cite{Jain2025:AMR} and a data-parallel ML training job, comparing with the overhead of
        full tracing.
        Evaluate ORCA in two configurations: a lightweight in-situ aggregation setup and a full
        configuration that persists all telemetry at tracing volume.
        The ML training job will be a data-parallel job running on a single node, and the AMR simulation
        will be run on a single node.
\end{itemize}

Additionally, an analysis of observability requirements identified from ML training literature,
demonstrating its compatibility with ORCA semantics, is ongoing.
This is not expected to have an experimental component.

\section{Timeline}

The thesis is expected to be completed by the end of 2025.
The following timeline is proposed:

\begin{itemize}
  \item July--Aug 2025: Complete distributed query planning and wrap up core development.
  \item Sept--Oct 2025: Evaluation, paper writing, and job search.
  \item Nov--Dec 2025: Complete and defend thesis.
\end{itemize}
